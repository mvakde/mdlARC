## Summary structure

The summary contains:

- <rules_summary>: the invariant input-to-output transformation
- <input_generation>: how valid input instances are constructed
- <variation_guidance>: properties that may safely vary
- <train_test_shift>: differences between the source training examples and the target test examples
- <solution_steps>: how an output is derived from an input
- <key_insight>: the central invariant
- <puzzle_concepts>: relevant concepts

The original solved task is primary evidence; the summary is an interpretation that may be wrong. Use <rules_summary>, <solution_steps>, and <key_insight> to describe the invariant family only where supported by the original. Surface properties may vary, but the underlying reasoning rule must not drift into a different ARC task.

For shape-to-color or pattern-to-label tasks, exact shape identity may be the rule. Preserve the demonstrated vocabulary; do not substitute component counts, areas, or another coincidentally matching statistic and then generate unrelated shapes. Teaching a broader rule in synthetic demonstrations does not establish that it belongs to the source family. Limited geometry variation is valid when the geometry is what the solver must recognize.

Use <input_generation> to construct valid input instances.

Use <variation_guidance> to introduce permitted diversity.

Use <train_test_shift> to create a meaningful difference between the generated training and test distributions.

## Puzzle coherence

The returned object is one ARC puzzle, not an unrelated collection of pairs.

Distinguish between:

- puzzle-level parameters, which remain consistent across all pairs
- pair-level parameters, which may vary from pair to pair

Infer this distinction from the source task.

For example, if a color mapping is learned from the source training outputs and then applied to the source test input, sample that mapping once for the whole generated puzzle. Demonstrate it unambiguously in the generated training pairs and apply it unchanged to every generated test pair.

Conversely, properties such as object position, grid dimensions, object count, spacing, corruption location, and particular motif arrangement may vary per pair when the summary permits them.

Do not randomize independently per pair any convention that the solver is supposed to learn across the task.

The generated training pairs must be mutually consistent. They must not imply different transformation rules or contradictory puzzle-level conventions.

## Core requirements

A generated puzzle must satisfy all of the following:
1. Every train and test pair uses the same underlying transformation rule.
2. Any puzzle-level convention affecting the test outputs must be demonstrated unambiguously by the generated training pairs.
3. Every generated test output must be uniquely determined by the complete generated training set together with that test input.
4. A solver must not need the generator seed, hidden generator state, random number generator, or internal puzzle_parameters object. Everything needed to infer the test outputs must be observable in the returned grids.
5. Pair-level random choices affecting an output must either be visible in that pair's input or determined by conventions demonstrated in the training pairs.
6. Ground-truth outputs must be generated by the same rule that a solver is expected to infer. Do not generate outputs using arbitrary inaccessible information.
7. The training pairs must provide enough evidence to distinguish the intended rule from reasonable alternative hypotheses.
8. The test pairs must exercise the shift described by <train_test_shift> without changing the underlying rule.
9. Do not create malformed, ambiguous, contradictory, or unsolvable puzzles.
10. Do not copy any original train or test pair exactly.
11. Every input and output grid must have between 1 and 30 rows and between 1 and 30 columns.
12. Every cell must be an integer color from 0 through 9.
13. Avoid degenerate pairs where input equals output unless unchanged examples are meaningful and explicitly supported by the source task.
14. Within one generated puzzle, avoid duplicate inputs and duplicate input/output pairs.
15. Preserve any invariant relationship between input and output dimensions demonstrated by the task.
16. Preserve the semantic role of background, structural, marker, object, and output colors, while allowing literal colors to vary only when permitted.

Within an individual puzzle, the training pairs must collectively demonstrate every puzzle-level convention needed to solve all its test pairs.

## Randomness and determinism

For a fixed seed and fixed count arguments, the complete generated puzzle must be deterministic.

Use:
    rng = np.random.default_rng(seed)

Do not use global random state.

Derive independent deterministic randomness for each pair. Do not pass the same unchanged seed or recreate the same random-number generator for every pair.

The same call must always return exactly the same grids:
    generate_puzzle(seed, num_train, num_test)

Different seeds should usually produce structurally different puzzles.

## Whole-puzzle recoverability

This is critical.

A test output does not necessarily need to be recoverable from its test input alone. It must be uniquely recoverable from:
    generated training input/output pairs + generated test input

The generator may use hidden puzzle-level parameters internally to construct ground truth only when those parameters are revealed unambiguously by the returned training pairs.

Invalid example:
- randomly choose whether red maps to blue or yellow
- generate only training pairs where no red object occurs
- place a red object in the test input
- use the hidden random choice to construct the test output

The solver has no evidence for the red mapping.

Valid example:
- randomly choose whether red maps to blue or yellow
- include one or more training pairs that visibly demonstrate the chosen
  mapping
- use the same mapping in every test output

For pair-specific masking, corruption, or erasure, enough information must exist either inside that input or through a convention demonstrated by the training pairs.

Invalid example:
- randomly generate a hidden pattern
- erase every occurrence of the pattern from the test input
- use hidden generator state to restore it in the test output
- provide no corresponding evidence in the training pairs

Valid example:
- generate several consistent repetitions of a pattern
- corrupt or mask only part of the pattern
- leave enough repetitions or training demonstrations to infer the missing
  content uniquely

Do not rely on information that exists only in the seed, random-number generator, or internal puzzle_parameters object.
