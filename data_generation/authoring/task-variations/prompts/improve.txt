## Whole-puzzle generation

Implement:

    generate_puzzle(
        seed: int,
        num_train: int | None = None,
        num_test: int | None = None,
    ) -> dict

Each call returns one complete solved ARC puzzle:

    {
        "train": [
            {"input": np.ndarray, "output": np.ndarray},
            ...
        ],
        "test": [
            {"input": np.ndarray, "output": np.ndarray},
            ...
        ],
    }

The test outputs are included because this program creates solved synthetic training data. The program will normally be called for approximately 30-40 seeds. Each call must return a coherent puzzle, not one isolated pair or a bag of unrelated pairs.

## Pair counts

Every generated puzzle must satisfy:

    1 <= num_test <= 4

If both counts are supplied, validate and use them exactly. If one is omitted, choose a legal value deterministically from the seed while honoring the supplied count. If both are omitted, choose a legal pair deterministically. Raise ValueError for illegal or impossible requests. Automatic counts must genuinely vary across seeds.

## Puzzle-level and pair-level parameters

At the beginning of generate_puzzle, sample conventions that a solver learns from the training set once for the whole puzzle. Examples include semantic color roles, direction conventions, marker meanings, color maps, ordering rules, or shared geometric constants. Only use conventions supported by the source family.

Then generate all training and test pairs using those conventions. Pair-level properties such as dimensions, positions, counts, spacing, scale, local geometry, and arrangement should vary independently when permitted. Do not randomize independently per pair anything the solver is supposed to learn across the task.

The generated training pairs must collectively reveal every puzzle-level convention needed to solve every test pair. They must remain mutually consistent and must not imply contradictory rules.

## Train and test regimes

Use regime "source_train" for puzzle["train"]. Training pairs must clearly demonstrate the rule, expose all puzzle-level conventions, preserve any real training-side restriction, and vary enough to prevent memorization of one layout.

Use regime "target_test" for puzzle["test"]. Test pairs must use the same rule and conventions, incorporate supported test-side shifts, remain uniquely solvable from the training demonstrations, and be new configurations rather than copies of source pairs.

If the source task has no meaningful train-test shift, draw test pairs from a more challenging or less common part of the same permitted variation space. Do not invent a new ARC concept just to make test pairs different.

## Core correctness requirements

A generated puzzle must satisfy all of the following:

1. Every pair uses the same invariant transformation rule.
2. Every convention affecting test outputs is demonstrated unambiguously by training pairs.
3. Every test output is uniquely determined by the complete generated training set and its test input.
4. A solver never needs the seed, RNG state, hidden parameters, or implementation details.
5. Pair-level choices affecting an output are visible in that input or established by training demonstrations.
6. Ground truth is built by the same rule a solver should infer.
7. Training evidence distinguishes the intended rule from reasonable alternatives.
8. Test pairs exercise the supported shift without changing the rule.
9. Puzzles are not malformed, ambiguous, contradictory, or unsolvable.
10. No generated pair exactly copies an original source pair.
11. Every grid has 1-30 rows and 1-30 columns.
12. Every cell is an integer ARC color from 0 through 9.
13. Input should not equal output unless unchanged examples are meaningful for this family.
14. A puzzle contains no duplicate inputs and no duplicate input/output pairs.
15. Input/output dimension relationships demonstrated by the task are preserved.
16. Background, structural, marker, object, and output color roles remain semantically correct.
17. Every correction and compatible diversity requirement from the human review is implemented.

## Diversity requirements

Structural and conceptual diversity matters more than superficial recoloring. Do not make every pair a translated, recolored, resized, or lightly perturbed copy of one layout.

Across seeds and, when compatible, within a puzzle, vary the broadest supported combination of:

- dimensions and aspect ratios
- object or region counts
- positions, spacing, orientation, and scale
- motif and boundary geometry
- sequence lengths and compartment layouts
- semantic color assignments
- corruption, masking, or incomplete-boundary patterns
- target-region position and dimensions
- repeated-structure counts and arrangements
- source-supported train/test shifts
- every variation axis called out by the human review

Avoid template banks with only a few hand-written layouts unless the source family itself has a finite vocabulary. Prefer compositional construction that can produce many structurally distinct valid configurations.

Across 42 fixed seeds, require substantial diversity in grids, layouts, dimensions, counts, puzzle-level parameter assignments, and review-requested properties. Tests for diversity must examine generated results or independently reconstructed properties, not merely values sampled into an internal dictionary.

Prevent source copies by comparing input/output grid contents, including shape. Do not ban all original grid dimensions, palettes, or layout categories to avoid exact copies. In particular, 30-by-30 source grids do not make new 30-by-30 grids invalid. The host compares actual source pairs and measures color-normalized, cropped structure as well as palettes and sizes. Distinct hashes alone do not demonstrate broad structural diversity: inspect feature distributions and combinations and remove unnecessary correlations or narrow ranges.

Within one puzzle, include meaningful diversity among pairs while keeping learned conventions stable. In particular, do not accidentally hold a pair-level property constant across all pairs when the human review asks for within-puzzle variation.

## Randomness and determinism

Use:

    rng = np.random.default_rng(seed)

For fixed seed and count arguments, the complete puzzle must be deterministic. Do not use global random state. Derive independent deterministic randomness for pairs without recreating the same RNG from the same unchanged seed. Different seeds should usually produce structurally different puzzles.

Use bounded construction and deterministic fallback logic. Avoid flaky rejection loops that can fail legal seeds or requested boundary counts.

## Whole-puzzle recoverability

A test output need not always be recoverable from its test input alone, but it must be uniquely recoverable from the generated training pairs plus that test input. Hidden puzzle-level parameters may be used internally to construct ground truth only when the returned training pairs reveal them unambiguously.

Do not choose a hidden color map, direction, pattern, or selection rule that is absent from training but needed at test time. Do not erase all evidence needed to reconstruct a masked test output. Validate that demonstrations cover every convention and every test-side case that requires learned information.

Perform a prediction check using only copies of training input/output pairs and a test input. Do not use any test output, seed, or generator metadata to infer the expected answer.
